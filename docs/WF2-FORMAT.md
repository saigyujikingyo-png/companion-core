# WF2 independent JSON format probe

This source implements a separate public engineering serialization probe. The two separately admitted actual runs and their negative results are recorded below; any later execution still requires a new source, profile, launcher and runtime admission. It does not read the old WF1 campaign or its sealed content. The WF1 negative calibration remains DS1 / Together0 / STOPPED with invalid JSON and zero teaching artifacts.

The profile `wf2-format-profile/2` fixes six independent requests before execution: two flat objects, two Unicode/escape objects, and two nested objects with twelve short engineering records each. Each request has an explicit system JSON instruction and complete syntax example. The user message consists only of the object to echo; the case ID remains in the local ledger and is not another object to serialize. They are serialization inputs, not teaching plans, answers, rubrics or evaluation cases. Each request has a fresh two-message context. No adaptive prompt, repair, retry, fallback or extra request exists.

Native `JSON.parse`, the existing strict integer/Unicode/duplicate-key JSON profile, and exact target preservation are three separate checks. `{}` cannot pass exact preservation. Syntax or preservation failures are recorded while the remaining preselected cases continue. Missing or inconsistent usage, transport UNKNOWN, provider/model failure, expiry, clock rollback, authority withdrawal or budget failure stops the run. All six requests must complete with all three checks passing to report `FORMAT_CASES_PASS`. That verdict covers these six cases only; it does not prove general JSON reliability or teaching quality.

Every call reserves 18,432 input tokens and 4,096 completion tokens at the frozen peak input/output prices of 300,000 / 1,200,000 micro-USD per million tokens. The frozen reservation estimate is 10,445 micro-USD per call, 62,670 for six, below the separate 100,000 micro-USD budget; it is not an invoice guarantee. Requests are non-streaming DeepSeek `deepseek-flash`, JSON object mode, thinking disabled, fixed native direct transport, one in flight, 120 seconds each and 15 minutes for the run. Reported usage is distinct from reserved cost and an actual invoice remains unknown. Missing usage stays unknown and never refunds a reservation.

`node src/wf2-format-worker.ts --describe` exposes the frozen profile, source dependency digest and trusted launcher protocol. A launcher supplies one closed bootstrap JSON document over anonymous stdin and ends stdin to submit it. This one-shot EOF is an input boundary, not an ongoing owner-disconnect signal. Actions are `prepare`, `run`, `inspect`, `pause`, and `cancel`. `prepare` is read-only; `run` creates a new dedicated ledger and never resumes an existing one; `inspect` only reads authenticated ledger claims and does not decrypt artifacts. Inspection always reports `RECORDED_CLAIMS_ONLY / RECONCILE_REQUIRED`, never a live format PASS.

The runtime and independent authority live outside the source tree and OneDrive. The trusted launcher supplies already admitted paths and a new random custody key; neither is an argument to a future DSH-facing tool. Before fetch, a dedicated WF2 ledger durably consumes the fixed route, complete request commitment, budget and case identity, then advances the independent host high-water under its lock. Response settlement and the next request require current authority again. A crash, unknown submission or stale authority cannot reopen the consumed run. An independent trusted control process can pause or cancel by changing authority; the active worker watches at 100 ms and aborts locally. This does not prove remote cancellation or refund. Host authority and encrypted storage reuse existing WF1 primitives without changing their bytes or semantics. Cooperative same-user custody is not hostile-user OS isolation, and a coordinated rollback of both ledger and authority is outside the protection claim.

Standard output contains only closed operational metadata: public case IDs, counts, status, three format checks, usage totals and cost estimates. It contains no credential, runtime path, request or response body, provider request ID, artifact reference or content commitment. Original encrypted request/response artifacts remain with the private run. No existing WF1 file, state, once marker, profile, source acceptance or evidence is upgraded by this probe.

Count completeness is explicit: `CURRENT_AUTHORITY`, `RECORDED_CLAIMS_ONLY`, or `STALE_OR_UNKNOWN`. If authority or a ledger commit becomes uncertain, authoritative call, usage and estimate totals are `null`; the last observed case list cannot establish a current zero or permit a refund. A successful cold inspection can report recorded totals, with its separate non-executable claims status.

The DSH integration is a separate service slice. DSH may deterministically dispatch a narrow pre-bound operation through its official CLI/plugin entrypoint; it must not add LLM calls, title/compaction, retries, arbitrary paths, credential access or sealed-content tools. A new teaching profile and dataset require task-specific independent admission, as documented in [the restricted formal-pilot decision](WF2-TEACHER-SERVICE.md). Student inference, training and public teaching-data publication are not implemented or authorized here.

Author verification: the initial 17 focused synthetic checks and strict TypeScript passed in normal-user Windows TEMP. Independent review then identified a stale-zero projection after a half commit; the projection now emits unknown totals and its final 18 checks and TypeScript passed, with a separate independent three-state recheck. The initial sandbox run encountered the existing authority atomic-rename `EPERM`; its evidence is retained and the production guard was not relaxed. Actual provider execution and cross-platform verification remain separate evidence categories.

The first independent actual profile/1 run completed its six preselected calls: native JSON and strict profile checks each passed six, exact-object preservation failed all six, so its result remains `NOT_PASSED`. A separately admitted offline classifier found five whole-user-envelope echoes and one other object; no reply was extracted or repaired to manufacture a pass. Profile/2 removed the user envelope and clarified that the entire user JSON object must be returned. It kept exactly the same six expected objects and all three acceptance checks, with a separately frozen protocol and independent admission.

The actual profile/2 run passed native JSON and strict profile checks for all six cases and exact echo for five. Unicode case 2 failed, so the run remains `NOT_PASSED`. A separately authorized authenticated offline comparison reported two fields exact and one value equal to the expected value's NFC form, with length decreased by one UTF-16 code unit. This is an observed value relationship, not proof of the provider's internal process. Combining-character sequences such as `e\u0301` and literal escape text such as `\\u0041` must not be assumed lossless merely because JSON parses. No normalization, extraction or repair is applied, and no third probe is authorized. Later formal-pilot acceptance uses its own unchanged exact typed-target oracle; neither negative format record is upgraded.
