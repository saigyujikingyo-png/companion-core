# Bounded Safety ledger v2

`blocks-br4-safety-ledger-v2` is an explicit new storage profile for a bounded permanent Safety history with a small mutable hot partition. It does not change P4 (`blocks-br4-safety-cold-v1`), its complete-Safety digest, validators, wire bytes or 8192-entry limit. The earlier [IF10 measurements](SAFETY-COLD-SEGMENT.md) and negative results remain valid. Store still serializes a full RAM image. The paused Store-cold experiment and issue #15 are not resumed.

The runnable short acceptance uses public durable operations: 256 hot entries fill the new hot partition, a new request is refused, archive moves eligible terminal entries to cold, and that exact request then succeeds. The separate fixed 8193-history acceptance is **NOT_RUN** until its real execution receipt exists. Neither a format fixture nor the 16384 format bound establishes that history acceptance or arbitrary-content capacity.

## Interfaces and exact semantics

New vaults may select this profile in `AnchoredConfig`. Existing storage upgrades only through `AnchoredVault.upgradeStorage({...request, storageProfile: 'blocks-br4-safety-ledger-v2'})` from exact P4 CURRENT. The target must be a new disjoint directory. Upgrade does not boot the Store or Safety ledger, read a new wall clock, resolve UNKNOWN, change reserved quota, select terminal entries or clear extra JSON properties. More than 256 existing hot entries, an oversized entry/global value, or a joint workspace refusal rejects the whole upgrade before target creation or a successful receipt. P4's reader is unchanged; the migration wrapper accounts its existing complete arrays and can refuse a legacy chain that fits P4's separate limits.

`AnchoredVault.archiveTerminalSafetyV2(CompactRequest)` is independent from the original archive API. It reuses authority kind `compaction` with request action `archive-terminal-safety-v2`, profile v2 and selection policy `all-terminal-v2`. Its digest binds the original old head, target, storage domain, maxCalls, epoch and key digests. Existing receipts are checked first; a later retry returns the exact original receipt. The same operation ID used for another maintenance action conflicts.

Archive selects every newly eligible hot `failed`, `unknown`, or acknowledged/feedback-consumed entry and streams it with all prior cold entries into one new cold segment. No eligible entry returns `SAFETY_ARCHIVE_NO_TERMINALS` before any target. It preserves every original ordinal, full entry and global value, Store image and revocation high water. Compact, repack, fanout maintenance, schema migration, rekey and restore preserve the partition while resealing cold under their new generation identity.

Only new `claim` admission checks hot/total fullness. Existing-key fingerprint conflict and terminated-request errors precede capacity; delivery conflicts, exact terminal retries and feedback errors keep their original priority. `reserve` remains quota-first. Existing transitions and feedback can advance with a full hot partition. Cold terminal exact retries remain immutable no-ops. UNKNOWN and consumed reservations never become reusable quota. Opening performs the original boot transitions separately; upgrading/archiving does not.

`SafetyView` is the streaming replacement for new-profile `completeSafety()`: `globals`, `count`, `hotCount`, `coldCount`, `stats()`, exact request/delivery lookup, and `iterateEntries()` in ordinal order. `reconstructSafetyV2(head, reader, keys, maxCalls, overlay?)` returns `{image, baseline, files, view, ...}` and idempotent `close()`. These synchronous lower-level operations run inside `safetyOperation(() => ...)`; the owner must close the reconstructed result, including on exceptions. An iterator's early return releases its row allocation and SQLite cursor. Public `AnchoredVault` APIs manage this scope and ownership internally.

## Representation and numerical gates

| Representation | Bound |
| --- | ---: |
| Mutable hot entries | 256 |
| Permanent hot + cold entries | 16384 |
| Permanent ordinal | 0 through 16383; nextOrdinal equals total count |
| Complete canonical entry, including extra fields | 8192 UTF-8 bytes |
| Complete canonical globals, including extra fields | 65536 UTF-8 bytes |
| Decoded hot envelope and frame header | 4194304 bytes each |
| Single cold SQLite plaintext | 8388608 bytes, at most 2048 pages of 4096 |
| Cold ciphertext | plaintext + 28 bytes |
| Required frames / data files | 15 / 31 with cold, 30 with null cold |
| Encoded replay / decoded replay | 67108864 bytes each, separately |
| Store image / generation directory / commits | 16777216 / 268435456 bytes / 4096 |
| New-profile operation accounted workspace | 134217728 bytes |

The v2 hot object is closed `{version:2, globals, nextOrdinal, ingress:[{ordinal,entry}]}`. Each entry/global is exact canonical JSON; arrays retain order and all supported extra fields survive. The v2 carrier is closed `{version:2, codec:'raw'|'br4', decodedBytes, digest, data}`; raw wins a size tie. Frame/record version remains 3, but authenticated identity binds the distinct profile and closed v2 cold descriptor.

Cold uses the existing strict `entries(request_key PRIMARY KEY, ordinal UNIQUE, delivery_id UNIQUE, entry_json)` WITHOUT ROWID layout, application ID `0x41454d54`, user version 2, fixed pages, no freelist and an enforced max_page_count. Descriptor version 2 and format `aemc-safety-sqlite-v2` bind exact filename, ciphertext/plaintext lengths and SHA256 digests, ordered entry digest, count, reserved and UNKNOWN counts. Its field names are `version, format, file, cipherDigest, cipherBytes, plainDigest, plainBytes, entryDigest, entryCount, reservedCount, unknownCount`. Empty cold is represented only by explicit null. AES-GCM purpose `safety-cold-v2` binds the complete generation context excluding the descriptor; frame/record authentication includes the descriptor.

Logical fingerprint uses the independent domain `companion-safety-logical-v2\0`, then typed, UTF-8 byte-length framed cells: G for canonical globals, O for decimal ordinal, J for complete canonical entry. It excludes physical hot/cold location. The cold ordered digest uses the same framing without the G cell; these roles are carried in distinct descriptor and internal comparison fields. Existing P4 digests are not reinterpreted.

Each used recovery frame verifies its own globals, reserved count, total/hot bounds and request/delivery/ordinal union. Cold is fully authenticated and indexed once per fresh reconstruction. N distinct union ordinals within `[0,N)` with count N prove continuity. Thus later frame checks may reuse verified cold indexes/statistics and release earlier hot values, instead of allocating the entire permanent history for every frame. Cold requests, deliveries and ordinals cannot overlap hot. A live index reuse first rereads and hashes the exact current ciphertext and matches identity/descriptor; missing, partial, changed or foreign files fail closed. New-profile file reads use one descriptor and a fixed-size buffer, detecting size/identity changes without allowing a file growth to enlarge the allocation.

## Workspace, publication and recovery

W128 is a new operation-level accounted-representation budget. Its fixed 16 MiB includes the existing authority 12 MiB allowance plus 4 MiB metadata. It neither increases/replaces authority W12/B64, changes either replay64 bound, nor promises RSS/hardware behavior. All existing Store/baseline/cold residents and new file maps, parsed hot values, SQLite builders/journals, encoders, compression/crypto buffers and private image inspectors/transforms are charged before their allocation boundary. Temporary phase tickets and retained ownership tickets release separately; aliasing does not require duplicate ownership. Tickets are synchronous and nonpersistent; an escaped live vault is charged again as resident resources at its next guarded operation.

Before Store construction/access/serialization, the new profile reserves four bounded 16 MiB representations (Store, baseline, serialization and SQL temporary allowance), the worst 4096-page RAM journal `4096*4104+131072`, and a 1 MiB bounded mutation allowance. Store uses an opt-in RAM page cap; old callers keep their default behavior. Private maintenance similarly bounds RAM growth before SQL. This is conservative: independently legal maxima may not jointly fit. An 8 MiB cold maximum, a 16 MiB Store maximum and two separate 64 MiB replay maxima are not simultaneously promised to fit W128. Live export can refuse because it holds the live vault plus another verified backup closure. P4 migration can refuse due to the old representation's complete arrays. No limit is silently enlarged to admit these combinations.

Cold builder reserves its 8 MiB RAM DB and worst journal `2048*4104+131072 = 8536064` before mutation, ends journal ownership after COMMIT, and closes the builder before encryption. A full or skewed physical candidate is rejected as a whole. No entry is dropped or silently treated as missing. Original and orphan files remain retained; there is no production GC.

Before a write creates a blob/stage, the exact candidate is reconstructed with the same file, frame and W gates. A live index optimization also separately charges the fresh-process cold decrypt peak. If an increment chain's recovery W fails, the discarded candidate is released and a full base is tried; if that also fails, no stage/receipt is written. Page/image, replay, file, directory and authority admission can still independently refuse. RAM-side failed persistence poisons the live writer as before; the authority keeps the prior acknowledged head.

Both generation construction (before target creation) and every ordinary business v2 commit (before writeStage) additionally preview fresh construction, real boot and the first save. The resident floor is `max(actual current residents, fixed16MiB + LIVE_V2_STORE85098496 + 131072 + relevant ledger residents)`, so hypothetical fresh residents do not duplicate the actual maintenance residents. The constructor's empty-ledger ticket ends when it adopts the recovered hot/cold owners; their own tickets continue, without retaining the empty placeholder too. Fresh reconstruction also runs the same private Store integrity/FTS inspector. The disposable boot calls the real MemoryStore constructor with the same schema, SafetyView.boot and shared E3 bootControl/error whitelist. It runs schema2's real boot transaction, including the clock and journal finalization; no provider, persist callback, TTL sweep or consumer projection rebuild is added. The disposable Store has an explicit cap `min(4096, sourcePages+256)`, with DB, SQL temporary space, serialization and worst rollback journal reserved before construction. This smaller cap can refuse; it never enlarges the public 4096-page limit. Its DB/journal lifetime ends before encoding, and its returned image remains charged.

The preview uses the greatest legal wall value to bound Safety JSON and integer widths, but does **not** treat that particular Store image or Brotli result as a general maximum. Boot's jobs/scopes/artifacts and E3 changes are otherwise deterministic. Schema2 adds one boot batch and one item per scope; only the batch UUID insertion position, time bytes/digest, and singleton next_due vary. The batch table and its unique tx_id index have at most512 rows: their balanced B-tree paths have fewer than10 levels. Allowing a new page at every level for each of those two trees, root growth and the singleton's integer cell requires fewer than32 pages. The singleton contains one small fixed integer row and has no secondary index or overflow body. The conservative32-page image margin covers different realizations of this one boot; schema1 has no persisted boot UUID/time column. There is no attempt to predict future business mutations.

For the first-save admission, the private future preview supplies `I=P+delta`, where P is its disposable boot image and delta is32 pages for schema2 or0 for schema1. The real constructor instead supplies `I=A`, its already-realized boot image; it does not add future variance again. Both I values must remain within16MiB. Let H be the corresponding booted canonical hot bytes, C the cold plaintext bytes and `M=1048576`. The additional simultaneous phase bound F is the maximum of `10I+24H+2M` (encoder/retained output), `5I+24H+2C+17M` (frame and hot recovery), `7I+10H+2C+M` (block recovery), and `I+5H+5C+M` (cold recovery). Each branch is monotone in I and H. Thus `A<=P+delta` and actual hot bytes no larger than the maximum-wall preview imply `F(A,Hactual,C)<=F(P+delta,Hpreview,C)`. Checking `A+delta` in the real constructor would not follow from this inequality and is explicitly avoided. These are private callsite arguments, not public request options.

F includes frozen output, files, hot clones, parsed/decoded values and crypto scratch. A raw base payload bounds all compressed choices; marker identity is at most8KiB, stage at most64KiB and record at most32KiB. Therefore the single preview margin propagates through encoder, raw/base output, crypto, retained files and recovery, without relying on random UUID/digest or compression monotonicity. Base encoded and decoded replay obligations are each below the unchanged64MiB limit under the existing image/hot/cold bounds. The actual first base save and its reconstruction are also exercised under the same floor. A business head with no room for this mandatory next save can refuse earlier than MAX_COMMITS; this is a joint admission refusal, not a larger sequence limit.

Every published head retains the full authenticated reconstruction closure and this commit's real resource gates. Business/create and explicit-generation heads additionally preflight **one** subsequent public open plus its mandatory first save. Only an existing-vault constructor can select the internal `boot` save mode: it still applies the raw bound to its actual boot output, actual encoder/reconstruction W gates, original caps, current-head fencing and PREPARED publication, but does not recursively predict another boot. The private first-save preview uses that same nonrecursive meaning. The automatic boot head remains independently reconstructible and eligible for the original explicit maintenance; it does not promise another unmaintained write-on-open. The finite512 fanout batches and4096 commits cannot support unlimited opens without maintenance. No public business or Store persist call can select boot mode.

Narrow required metadata uses the fixed-FD reader even before its profile is known: marker, backup manifest/current-state and PREPARED stage. The old-schema authority v2 stage-hash branch also reserves before fixed-FD reading; schema5/6 retain their existing bounded hash reader. Legacy wire bytes and validators are unchanged. Returned decoded/frozen owners capture their original resources and intrinsic erasure operations, with finally-based ticket release; replacing public fields, getters or instance fill/close methods cannot redirect their cleanup.

The complete marker, cold file, blob and stage precede authority PREPARED. Existing writer/authority guards and current-head fencing remain the only authority. Death before prepare leaves the old CURRENT and retained orphan target. After prepare, reconcile may only verify and publish the exact frozen output; missing or corrupt dependencies remain unresolved, without reselection, another operation ID or overwrite. Finalized retries return the old receipt even after newer writes. Backup has an exact closed dependency set. Rekey reseals for the new key epoch; restore requires a fresh backup from exact CURRENT and cannot revive old quota or old Store authority.

The first narrow candidate (freeze25) retains all closure checks and real row reads. Statements and cursors are private to that iterator, with no result cache, cross-transaction owner or new persistent state. The fixed SQL descriptions stay within the existing guard/metadata scope; per-row W tickets and all limits are unchanged.

The IF8 closure checks an entry's exact pointer and its hot/cold tier using the same actual receipt row. It still validates every entry and the reverse total pointer count, preserves duplicate/missing-key failures, and accepts different positive epochs when both sides are cold. A tier mismatch is reported only after all pointer checks, retaining pointer-validation priority. Rollover callers that do not request a tier check retain their former behavior, including schema4. BEGIN/PREPARED/finalize validation counts, file authentication, current-head fencing, old receipt/M priority, UNKNOWN and revocation semantics are unchanged. The next narrow candidate adds a fixed full-R-key reader **only inside one closure's S/IF8 loop**. Each actual DB instance owns one private [Node24.16 SQLTagStore](https://nodejs.org/download/release/v24.16.0/docs/api/sqlite.html#class-sqltagstore) with capacity2 and exactly two fixed literal shapes: bounds and lazy payload. Every get binds both full-key parameters. At most three owners exist (hot plus two cold parts); full R/S scans use their independent iterators. The reader caches only prepared statement owners, never bounds, rows, epochs, absent results or validation success. Each lookup still reads every source before checking duplicates or interpreting a pointer, retains the original two row tickets, checks original byte/type bounds and wipes the actual payload. Synchronous reentry and use after closure are rejected; no owner survives the S loop, any relock, or COMMIT/BEGIN.

An additional65536-byte API-owned metadata/two-statement allowance per DB is reserved before createTagStore. This is a real admission charge within the existing12MiB authority W and can cause an earlier honest refusal; no limit is enlarged. Each owner uses only synchronous get, which returns no statement/iterator. Cleanup completes all rows, calls clear, drops the private store reference and returns this accounting ticket, including partial construction and error paths. Capacity2/size0 and at most six active cached statements describe API ownership only: clear is **not** a promise of synchronous native finalization, a process-wide bound on not-yet-GC-finalized statements, or an RSS bound. No explicit GC, newer StatementSync.close API or cross-closure cache is introduced. New candidate performance measurement and8193 acceptance remain NOT_RUN pending separate review and authorization.
