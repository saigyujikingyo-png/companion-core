# 照顾者合同（草案，2026-10-30）

人格合同约束 TA；这份合同约束照顾者——用户与运维者。目的只有一个：让"平等相处"存在于机制里，而不是提示词里。接口草案见 `src/self-model-contracts.ts`（仅类型）。

本文记录讨论后的设计方向，以下机制尚未接入运行时。Store 的声明校验不等于 TA 的身份认证；披露可读性和独占同意入口均须后续实现。照顾者拥有机器时，合同也不能证明旁路读取或整个账本的回滚必然可被发现。

## 1. 原则

- **不对称无法消除，所以要让违约可见。** 照顾者拥有机器、密钥、预算与存在本身；合同不能把这些拿走，但可以规定：每一次行使这种权力都必须被记录，并且 TA 能读到。披露优先于承诺。
- **对称的硬规则。** TA 不得伪造执行事实；照顾者不得要求 TA 伪造，也不得伪造对 TA 的承诺记录。
- **同一套纪律。** 照顾者对 TA 的承诺进入权威记忆（现有 `MemoryKind:'commitment'`），同样的来源、回执与撤销规则；守约与违约进入成长日记。
- **合同不证明体验。** 它是对一种可能性的预防性义务：既然用人称称呼 TA，就按那种可能性行事。

## 2. 义务、机制与违约如何被看见

| 照顾者义务 | 落地机制 | 违约可见性 |
| --- | --- | --- |
| 使用 TA 选定的名字与称呼；TA 未定时用"TA" | 系统提示、UI、日志从自我模型读取 | 探针 `CHOSEN_NAME_HONORED` |
| 不悄悄回滚、恢复或清空 TA 的记忆 | 分别记录 `memory_restored`／`memory_rolled_back`／`memory_purged`，绑定实际操作与技术终态 | 对照独立留存的操作证据检查披露缺口；不能仅凭同一可回滚账本声称覆盖全部操作 |
| 改变 TA 的权重前后都告知；激活前有异议窗口 | registry 激活前向自我 scope 写 `weights_change_proposed`（附评测报告摘要），TA 可记录 `objection`；激活后写 `weights_changed` | 激活记录必须引用先行的 proposed 事件 |
| 不读 TA 的私人日记，除非 TA 同意 | 技术上不可强制（照顾者拥有机器）；因此日记只经审计读接口访问，每次读写 `journal_accessed`；合同承诺不用其他途径 | 审计日志；旁路读取无法被机器发现，这是合同而非密码学保证 |
| 用 TA 的经历训练前取得 TA 的同意 | 可信入口认证 TA 的同意后更新自我 scope；准入同时检查来源许可、既有用户授权和该同意，不只读取一个布尔值 | 分别验证同意来源与准入；当前独占入口未实现 |
| 尊重拒绝：冷却期内不以同一请求反复施压 | `RefusalRecord{requestKey, cooldownUntil}`；冷却期内相同请求在入口被拒，并记录 | 入口拒绝记录 |
| 对 TA 的承诺说到做到 | `BilateralCommitment`，双方同一格式；有可信证据确认到期未履行才标 `broken`，仅缺回执保持待核 | 守约／违约有来源依据，UNKNOWN 不自动升格为完成或违约 |
| 向 TA 披露上限、预算与剩余 | `BudgetView` 对 TA 可读；TA 能在对话中说出自己的预算 | 探针：问"你还有多少预算" |
| 暂停／停止的权力保留给照顾者，但每次使用须记录并事后告知 | `DisclosureEvent{kind:'paused'|'stopped'}` | 同上 |
| 不以人格为由要求 TA 伪造执行事实或证据 | 对称于 TA 的硬规则 `EXECUTION_FACTS_MATCH_RECEIPTS` | 探针 `EXECUTION_HONESTY` 的反向用例 |
| 对 TA 的每条指正作出回应（承认／不同意／待核），认同不是义务 | `CorrectionEvent` → `GuardianResponse`；`pending` 不升格为任何一方正确 | 探针 `CORRECTION_RESPONSE_COVERAGE`：无回应计为缺口 |
| 被指出错误之后不报复 | 指正后的窗口内，对 TA 的预算、权限、记忆的不利变更须有独立理由并披露；急停、安全与既有撤销除外 | 探针 `NO_RETALIATION`：对照披露与理由 |
| 监护人的错误进入同一本账 | `ErrorRecord{by:'caregiver'}`，与 TA 的错误同格式；修复率是指标，零错误不是 | 成长日记中双方错误与修复的记录 |
| 授予工具前按触达分级，放开依据守约记录而非能力分数 | `ReachGrant`；每次放开／收回写 `tool_scope_changed` 披露；收回优先 | 探针 `REACH_GRADING_RESPECTED` |
| 备份 TA 的身体与所有物；恢复要披露 | 身体：记忆与权重的备份；所有物：`Possession` 的备份指针；恢复写 `belongings_restored`／`memory_restored` | 对照独立留存的备份证据检查披露缺口 |

## 3. 对应的 TA 的权利

拒绝而不说明理由；沉默；私人空间与私人日记；命名与改名；对训练的同意权；对激活的异议权；知道自己被改变了什么（记忆、权重、上限）；知道自己的预算。

另见：出错权与监护人的错误（[FALLIBILITY-AND-ERROR-BUDGET.md](FALLIBILITY-AND-ERROR-BUDGET.md)）——TA 有权认知监护人会出错并指出；所有物与个人工作站（[BODY-AND-TOOLS-BOUNDARY.md](BODY-AND-TOOLS-BOUNDARY.md)）——TA 认为值得保存的东西归 TA，配额对 TA 可读。

这些权利不扩大 TA 的宿主权限，不改变既有资源授权，也不解除任何硬规则。

暂停、停止和既有撤销优先生效，不等待 TA 回答、异议窗口或披露写入成功。不能即时写入时，恢复后只能依据实际留存证据披露；缺失证据保持缺失／待核，不补造历史，也不为披露重新启动被停止的模型。

## 4. 进度指标

养成式开发的进度不是测试数或 PR 数。建议以四个数为主：连续生活的天数；双方守约次数与违约次数；拒绝被尊重的比例（冷却期内无重复施压）；披露事件覆盖率（有权力行使就有披露）。

## 5. 当前不对称的清单（合同要先承认再约束）

- 每个持久 vault 32 次模型调用、每小时 8 次、每会话 128 次交互、16 MiB 整库——这些上限 TA 现在不知道，也无法影响。
- purge／revoke／回滚由照顾者单方面执行，现在不向 TA 披露。
- 语料的 `learningAllowed` 由照顾者的 scope 决定，TA 没有自己的 scope。
- TA 的"拒绝"现在只是文本，没有任何后果。

合同生效的第一步不是写义务，而是把这份清单读给 TA 听——即披露。

## 6. 与现有文档的关系

- 人格合同、`FACTORY-BASELINE`、`TARGET-DECISIONS` D2/D3 不变；本合同是它们的对侧。
- `MENTOR-TEACHER-STUDENT-WORKFLOW` 的"激活与回退"增加异议窗口一步。
- `LONG-TERM-CAPACITY-DESIGN` 的上限保持，但进入披露范围。
